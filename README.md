# L76148/moon-ron

A strict RON parser, serializer, formatter, and typed codec for MoonBit.

The current implementation provides six independently verified capabilities:
parsing a RON document into a dynamically typed `RonValue`, serializing that
value back to compact canonical RON text, formatting structured values as
readable multiline RON, converting between RON values and typed MoonBit values
through `FromRon` and `ToRon`, applying document extension attributes, and
checking or formatting files through a CLI.

The library core has no runtime dependencies. The CLI uses the official
`moonbitlang/x/fs` package for file access.

## Install

```text
moon add L76148/moon-ron@0.1.1
```

## Why RON

MoonBit already has established packages for JSON, TOML, YAML, KDL, and HCL.
RON occupies a distinct point in that space: it keeps Rust-style structs,
tuple variants, enums, options, bytes, and comments while remaining readable
as configuration data. An independent MoonBit implementation makes it useful
for test fixtures, game data, and exchange files generated by Rust services.

## Supported syntax

- Unit, booleans, characters, strings, byte strings, byte characters
- Signed integers, unsigned integers, floats, infinities, and NaN
- Sequences, tuples, maps, named structs, tuple structs, and enum variants
- Closed, open-ended, and inclusive ranges
- `Some`, `None`, line comments, nested block comments, and raw strings
- Bounded nesting depth and source-positioned errors

## Use

```text
let value = @ron.parse(
  "Point(x: 1, y: 2, tags: [\"parser\", \"ron\"])",
)
let source = @ron.to_string(value)
let readable = @ron.to_string_pretty(value, indent=2)
```

Typed values implement two traits:

```text
impl @ron.ToRon for Point with fn to_ron(self, options) { ... }
impl @ron.FromRon for Point with fn from_ron(value, path, options) { ... }

let source = @ron.encode(point)
let point : Point = @ron.decode(source)
```

The root package exports:

- `parse(source, max_nesting_depth?)`
- `to_string(value)`
- `to_string_pretty(value, indent?)`
- `decode[T](source, max_nesting_depth?)`
- `decode_with_options[T](source, options?)`
- `encode[T](value)`
- `encode_with_options[T](value, options?)`
- `FromRon` and `ToRon`
- `valid(source)`
- `parse_document(source, options?)`
- `RonValue`, `RonNumber`, `RonPosition`, `RonError`, `RonPath`, and
  `RonDecodeError`
- `RonExtensions`, `RonOptions`, and `RonDocument`
- `render_error(source, error)` and `render_decode_error(source, error)`

## MON: data in MoonBit syntax

The `mon` package adds MON, a data notation whose literals are the literals of
MoonBit itself, so a data document reads like the code around it:

```text
Config {
  name: "api",
  ports: [8080, 8081],
  limits: { "cpu": 4, "memory": 1024U },
  window: 1..=10,
  owner: Some(Point { x: 1, y: 2 }),
  banner: (
    #|MON reads data written the way
    #|MoonBit writes its literals.
  ),
}
```

```text
let value = @mon.parse(source)
@mon.valid(source)
@mon.render_error(source, error)
let source = @mon.to_string(value)
let readable = @mon.to_string_pretty(value, indent=2)
```

Every accepted literal is checked against the MoonBit compiler: `#|`
multiline strings, `\x` byte escapes, `L`/`U`/`UL` integer suffixes, and
`\u{...}` escapes are read the way MoonBit reads them, and the spellings
MoonBit rejects (`'\0'`, `"\v"`, `1e10`, `1l`, `/* */`) are rejected here too.
`docs/MON.md` records the mapping form by form. Only two spellings go beyond an
expression, because a data document needs them: `Name { field: value }` and
the `..`/`..=` ranges.

Run the MON reader over the fixtures:

```text
moon run cmd/mon -- check corpus/mon/config.mon
moon run cmd/mon -- check corpus/mon/services.mon
moon run cmd/mon -- check corpus/mon/scalars.mon
moon run cmd/mon -- compact corpus/mon/config.mon
moon run cmd/mon -- format corpus/mon/services.mon
```

A document can also ask for text before it is read: `#include "path"` splices
another document and `#env "NAME" (fallback)` substitutes a variable, both
resolved through an injected environment, so `mon expand` assembles a document
out of a directory and the process environment. `to_moonbit_source` goes the
other way: it writes the MoonBit binding that holds a value, which is how a
`.mon` file is inlined into a program instead of being parsed at start-up.
`cmd/embedded` is a working example, and CI regenerates its source from
`corpus/mon/embedded.mon` and fails when the result differs.

```text
moon run cmd/mon -- expand corpus/mon/deployment.mon
moon run cmd/mon -- gen corpus/mon/embedded.mon config Config
moon run cmd/embedded
```

MON ships in this module; the published `0.1.1` release predates it.

## Design notes

The parser keeps syntax and semantic conversion separate. `RonValue` is a
lossless-enough generic tree for parsing, inspection, and future conversion.
The serializer emits compact deterministic syntax and keeps numeric type
boundaries across a parse/serialize round trip. Typed decoding will be added
as a separate trait layer instead of complicating either operation.

The `mon` package follows the same split: its lexer, parser, and `MonValue`
never depend on RON, so the two notations can be kept honest on their own and
joined later by a conversion layer instead of by shared shortcuts.
